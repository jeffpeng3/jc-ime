# 候選上限（`max_candidates`）對單鍵延遲的影響

> 相關：[candidate-unify.md](candidate-unify.md)（版面、移動與上限的產品規則）。
> 本文的結論已被採用：`DEFAULT_MAX_CANDIDATES = 200`（固定值、不做設定）。

量測 `SessionConfig::max_candidates` 設 20／40／80／200／500 時，注音單鍵
`Session::press` 的延遲、開候選窗（↓）的延遲、候選實際長度、State JSON 大小
與候選記憶體，回答「提高到 200 值不值得、要不要做成設定」。

## 結論

- **40 → 200 的單鍵成本是 +0.05～0.11 ms（p50）**，最差的一組是
  `ㄧˋ` 0.766 → 0.880 ms；全部仍低於 1 ms，距 16.7 ms 的影格預算很遠。
- 成本**近似線性於「實際候選數」，不是 k 本身**：每 100 個候選約
  +0.050～0.071 ms。候選數受詞典封頂後就完全平坦（`ㄕˋ` 在 k=200 與
  500 都是 146 個，延遲差 +0.004 ms）。
- **200 的記憶體與線路大小可接受**：候選陣列約 14～21 KB、`Response::State`
  JSON 12～22 KB、序列化 0.03～0.05 ms。最差單鍵總成本（press＋序列化）
  約 0.93 ms。
- **建議：固定提高到 200，不做使用者設定**。200 → 500 只多出極罕用候選，
  卻讓 `ㄧˋ` 的 State 從 16.8 KB 漲到 27.6 KB；「到達上限才擴充」要多一層
  狀態與 IPC 流程，換不到 0.1 ms。做成設定則把 <0.1 ms 的取捨丟給使用者，
  還得多維護設定契約與 UI，不值得。
- 4 欄版面一頁 40 項，量測當時的預設 20 連第一頁都填不滿；提高到 200 同時
  解決
  這個問題（4 欄 = 5 頁）。

## 量測方法

- 機器：GB10（aarch64，20 核，128 GB UMA），Linux。
- 建置：`cargo test --release`（release，非 debug）。
- 資料：`/mnt/work/jc/jc-ime-data`（注音詞典 271,170 條、bigram LM、
  zh-select 模型已安裝）。
- 模式：`Mode::Mixed`，透過 `SessionConfig` 只改 `max_candidates`；
  其餘沿用引擎 `EngineData::session_config`（含 bigram 與選字模型）。
  `learning = false` 固定候選順序。
- 按鍵：標準（大千）排列，由 `Keyboard::standard().keys()` 產生：
  `ㄨㄛˇ` = `ji3`、`ㄕˋ` = `g4`、`ㄧˋ` = `u4`、
  `ㄊㄞˊㄨㄢˊ` = `w96j06`。
- 每一組 (k, 音節) 跑 3 輪；每輪 200 次「開新 session → 打完音節 →
  按 ↓」，每次都重新建立 session。表格取 3 輪 p50／p95 的中位數，
  max 取三輪最大值。每輪開始前另外預熱 30 次（不計入樣本）。
- 「單鍵」指**完成音節的最後一鍵**（聲調鍵），那一鍵才會重建詞格、
  跑 nbest 與候選排序；前段注音鍵多半只更新暫存，單獨列出會被拉低，
  不適合當代表。
- `State JSON` 是 `serde_json::to_vec(&Response::state(snapshot))` 的
  位元組數，也就是引擎實際送給外殼的內容；序列化時間另外量。
- 重跑：`scripts/bench-nbest-k.sh`（見文末）。

## 單鍵延遲

完成音節那一鍵，單位 ms，格式 `p50 / p95 / max`：

| k | ㄨㄛˇ | ㄕˋ | ㄧˋ | ㄊㄞˊㄨㄢˊ |
|---|---|---|---|---|
| 20 | 0.028 / 0.029 / 0.034 | 0.521 / 0.546 / 0.557 | 0.753 / 0.778 / 2.607 | 0.281 / 0.284 / 0.292 |
| 40 | 0.028 / 0.029 / 0.032 | 0.521 / 0.532 / 0.548 | 0.766 / 0.784 / 0.800 | 0.296 / 0.300 / 0.334 |
| 80 | 0.028 / 0.029 / 0.033 | 0.530 / 0.545 / 0.989 | 0.800 / 0.813 / 0.842 | 0.321 / 0.324 / 0.330 |
| 200 | 0.028 / 0.029 / 0.032 | 0.573 / 0.590 / 0.617 | 0.880 / 0.902 / 0.917 | 0.405 / 0.417 / 0.434 |
| 500 | 0.029 / 0.031 / 0.035 | 0.577 / 0.589 / 0.627 | 0.956 / 1.009 / 1.867 | 0.425 / 0.459 / 0.479 |

`ㄨㄛˇ` 的字典只有 9 個候選，k 再大也沒有工作可做，可當控制組：五個 k 的
p50 都在 0.028～0.029 ms，與 k 無關，說明其他讀音的增量不是量測漂移。

`ㄧˋ` 的絕對值比 `ㄕˋ` 高，是這個讀音的詞格本身較大（20 個候選時就
0.75 ms），不是 k 造成；看 k 的增量即可。重跑之間 p50 約有 ±0.02 ms
的變動，不影響量級。

## 開候選窗（↓）

第一次按 ↓ 的延遲，單位 ms，格式 `p50 / p95 / max`：

| k | ㄨㄛˇ | ㄕˋ | ㄧˋ | ㄊㄞˊㄨㄢˊ |
|---|---|---|---|---|
| 20 | 0.040 / 0.041 / 0.044 | 0.233 / 0.238 / 0.260 | 0.491 / 0.504 / 2.172 | 0.095 / 0.100 / 0.103 |
| 40 | 0.040 / 0.041 / 0.045 | 0.246 / 0.251 / 0.273 | 0.510 / 0.519 / 0.577 | 0.100 / 0.104 / 0.112 |
| 80 | 0.040 / 0.041 / 0.059 | 0.256 / 0.259 / 0.279 | 0.553 / 0.561 / 0.574 | 0.104 / 0.108 / 0.112 |
| 200 | 0.040 / 0.040 / 0.044 | 0.304 / 0.309 / 0.323 | 0.686 / 0.703 / 0.712 | 0.109 / 0.112 / 0.118 |
| 500 | 0.041 / 0.042 / 0.044 | 0.304 / 0.309 / 0.328 | 0.819 / 0.840 / 0.852 | 0.110 / 0.115 / 0.125 |

↓ 的增量比單鍵明顯（`ㄧˋ` 40 → 200 是 +0.176 ms），但絕對值仍不到
1 ms。`ㄊㄞˊㄨㄢˊ` 幾乎不變，因為 ↓ 只展開游標所在的那一個音節，
那個音節的候選數沒有隨 k 增加。

## 40 → 200 的增量與線性

| 音節 | 40 p50 | 200 p50 | 增量 | 候選數 40 → 200 | 每 100 個候選 |
|---|---|---|---|---|---|
| ㄨㄛˇ | 0.028 | 0.028 | +0.000 ms | 9 → 9 | —（已封頂） |
| ㄕˋ | 0.521 | 0.573 | +0.053 ms | 40 → 146 | +0.050 ms |
| ㄧˋ | 0.766 | 0.880 | +0.114 ms | 40 → 200 | +0.071 ms |
| ㄊㄞˊㄨㄢˊ | 0.296 | 0.405 | +0.109 ms | 40 → 200 | +0.068 ms |

- 不是「k 每加 1 就固定加多少」，而是**每個實際算出來的候選約 0.5～0.7 µs**。
  線性關係在候選數上成立；k 超過詞典上限後自然飽和。
- `ㄕˋ` 在 200 與 500 的候選數都是 146，延遲 0.573 → 0.577 ms，等於沒有差別。
- 200 → 500 只剩 `ㄧˋ`（200 → 330）與 `ㄊㄞˊㄨㄢˊ`（200 → 240）多算，
  單鍵增加 0.076／0.020 ms，換來的是最尾端極罕用的字。

  capacity，不含 nbest 內部暫時配置（那些在 press 回傳前就釋放）。
- 200 時最差單鍵總成本：0.880 ms（press）＋ 0.047 ms（序列化）≈ 0.93 ms。
  500 時 0.956 ＋ 0.078 ≈ 1.03 ms。
- IPC 量：假設每秒 10 鍵，200 時約 120～220 KB/s，500 時約 280 KB/s；
  named pipe 與一般外殼都吃得下。

## 建議

**把固定上限提高到 200，不新增設定。**

理由：

1. 成本上限明確：最差 +0.11 ms／鍵、+0.18 ms／開窗，遠低於可感知門檻，
   也遠低於既有 5 ms 的單鍵預算（`long_run_latency`）。
2. 200 才真正覆蓋「候選很多」的音節：`ㄕˋ` 146、`ㄧˋ` 200、`ㄊㄞˊㄨㄢˊ`
   240 都是 40 看不到的。500 只多算 40～130 個極罕用候選。
3. 設定化沒有對價：使用者選 20／40 省不到 0.1 ms，卻要付出設定檔欄位、
   JSON 契約、UI、說明與測試成本；選 500 也只換到更長的稀有字清單。
4. 「到達上限才擴充」（先算 40，使用者翻到底再補算）要多保存一輪請求狀態、
   多一次非同步或阻塞補算，還要處理補算期間的選字索引；省下的 0.1 ms
   不值得這個複雜度。

若團隊不接受 200，最低應是 **40**：4 欄 × 10 列一頁就是 40 項，量測當時的
預設 20 連第一頁都填不滿。

若只想要最小改動，**固定 40** 也可接受；但 `ㄧˋ` 這類讀音仍有 160 個
常用度不差的候選看不到，而成本只差 0.1 ms。

## 風險與注意事項

- **UX 噪音**：上限 200 表示直向單欄有 20 頁、4 欄有 5 頁，往後翻會看到
  愈來愈罕用的字。第一頁不變，但「還有幾頁」變多。若不希望使用者翻到
  罕用字，應在顯示層過濾，而不是把上限壓回 40。
- **State 變大**：每鍵 JSON 從 3.5 KB 漲到 12～22 KB（500 時 27 KB）。
  目前序列化只要 0.03～0.05 ms，但外殼若對每個 snapshot 做額外複製或
  記錄，成本會跟著放大。
- **候選品質不會因此變好**：提高上限只增加尾端候選，前 8 名在五個 k
  完全相同（量測中四組讀音都一樣）。若目標是「排序變好」，要提高的是
  模型或成本，不是 k。
- **max 值有排程抖動**：不同輪次在 k=20／40／500 都出現過 1～4 ms 的
  單次尖峰，p50／p95 不受影響；最大值不適合當 k 的回歸門檻，建議用 p95。
- **平台差異**：數字來自 GB10（aarch64）release。x86 Windows 的絕對值
  可能不同，但「每候選 0.5～0.7 µs、200 的增量約 0.1 ms」這種量級應一致。
- **選字模型行為**：目前 zh-select 只重排首選，所以 k 不會讓模型成本
  線性成長。若未來改成對全部候選推論，這個結論要重量。

## 重跑方式

```sh
scripts/bench-nbest-k.sh
# 或指定資料根目錄
JC_TESTDATA=/path/to/jc-ime-data scripts/bench-nbest-k.sh
```

腳本會把 `scripts/nbest_k_cap.rs` 暫時複製到
`crates/jc-engine/tests/nbest_k_cap.rs`，用 release 建置執行，結束後刪除；
每列輸出是 `RESULT <json>`，表格由這些數字整理。需要
`/mnt/work/jc/jc-ime-data`（或 `JC_TESTDATA`）與已安裝的 zh-select 模型；
沒有資料時直接失敗，不會產生空表。
